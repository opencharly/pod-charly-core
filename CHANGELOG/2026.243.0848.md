# 2026.243.0848 — chore: advance stale pins so published tags carry current refs

## Summary

Advances this repo's one stale pin. A published tag embeds the pins it carried at tag time,
so consumers pinning a tag of this candy drag its old refs into their own resolution and
charly reports `resolved to multiple versions` on every build of that consumer.

The diff changes exactly **two** values, both in `charly.yml` — nothing else:

```
  @github.com/opencharly/charly/candy/direnv   v2026.183.1359 -> v2026.243.0812
  version (this candy's own CalVer)            2026.243.0830  -> 2026.243.0846
```

Note the ref carries a **subpath** (`charly/candy/direnv`), not the bare repo `charly`. The
commit message's aligned table abbreviates it to its owning repo; the full ref is the one
above and is what the diff shows. The candy's own CalVer advances because the pin change is
changed content, which must ship under a new version rather than reuse a released one —
`2026.243.0846` sorts strictly after the `2026.243.0830` main carries.


No packages, services or plan steps change.

### Why the previous attempt was closed

PR #6 proposed a **version-only** diff with no pin advance at all, and was correctly blocked
for claiming advances its diff did not contain. Two defects in the sweep tooling caused that,
both now fixed and both verified before this PR was opened:

1. **Subpath refs were never rewritten.** The rewrite pattern was built from the repo name
   alone, so `/charly:` could not match `/charly/candy/direnv:`. This pin was therefore
   skipped by every earlier wave — which is why this repo was re-flagged stale on each
   rescan and never converged. The pattern now allows an optional subpath, and was tested
   against subpath refs, bare refs, and double-quoted refs, with `charly-other` as a
   negative control to confirm a repo whose name merely *starts with* `charly` is untouched.
2. **The version bump was not gated on a real pin change.** The no-change check ran *after*
   the bump, so it could never fire: the bump always dirtied the file. The gate now tests the
   pin edits alone and skips the repo when the pins are already current.
