# 2026.243.1552 — docs(deploy): explain member-to-member resolution and how it dies silently

## Summary

The `deploy` skill documents auto port mapping in detail but never says **how one member of a
fleet reaches another**. That left the two mechanisms as folklore, and left their failure modes
undocumented — which cost real debugging time.

Two mechanisms exist, and they fail differently:

1. **By member name** (`charly-<bed>-<member>`) — an ordinary NSS/`getent hosts` lookup inside
   the venue, served by `aardvark-dns`. Readable and portable; required when a peer must be
   addressed by name.
2. **By resolved host port** — `${HOST_PORT:N}`, the loopback mapping the skill already
   documents. **No name resolution is involved at all.**

## Why this needed writing down

Member-name resolution depends on `aardvark-dns` running in the namespace podman is *currently*
using. podman tears the rootless netns down when the container count reaches zero and creates a
fresh one on the next start — but does not restart aardvark, which keeps serving the dead one.

The result is a failure that looks like anything except DNS:

- the aardvark process is alive
- the bridge is up in the new namespace with the correct gateway
- the zone file is correct and **lists the new containers** by name and IP
- `podman network inspect` reports `dns_enabled=true`
- and every `getent hosts <peer>` returns empty

**A disposable bed causes this routinely**, because its teardown removes the last containers on
an idle host. So the breakage appears in the NEXT run, after a green one — making the change
under test and the bed that just passed both look guilty when neither is. It is also host-wide:
other sessions' beds fail at the same moment for the same reason.

This was diagnosed the long way — through the change under test, the bed's mount configuration,
and podman's overlay store — before anyone compared namespaces. The section exists so the next
person compares namespaces first.

## What the section adds

- both mechanisms, stated plainly, with when to choose each
- the full list of things that still look healthy while DNS is dead
- a two-command diagnosis:

  ```bash
  readlink /proc/$(pgrep -x aardvark-dns)/ns/net
  podman unshare --rootless-netns readlink /proc/self/ns/net
  ```

- a pointer to the `charly doctor` check that now reports it (`aardvark-dns namespace
  STRANDED`, opencharly/plugin-doctor#4)
- recovery **including removing the stale pidfile** — without that, podman believes a healthy
  daemon is running and starts no replacement
- guidance: prefer `${HOST_PORT:N}` when a step only needs to *reach* a peer, since it has no
  DNS dependency and cannot fail this way
